## 中文

`1.0.0` 已正式发布，范围是 Search 响应协议修复。它修复 `grok-4.6` 在真实 Web/X Search 流中仍可能触发的 `The Grok provider rejected an invalid or unsupported response`：上游可能在一次 Search 完成后，让同一 reasoning ID 继续出现为多个空占位生命周期；完成态 Web Search 也可能返回 `open_page` action。

> 当前 npm 稳定版和 `latest` 均为 `1.0.0`。最终 release commit 为 `c6548199582b122f1d285422eabea0205eaf602f`；final CI run `33308603394` 的 macOS 14 / Windows 2022 均通过，Trusted Publisher run `33309083806` attempt 1 已发布仓库所有者明确授权的精确制品。

### 安装

当前稳定版：

```sh
dsh plugin --profile web add dsh-grok-provider@1.0.0
dsh web
```

### 修复内容

- 首次复用 reasoning ID 前，原 lifecycle 必须闭合，并且两者之间必须有一个完成的 Web/X server Search。
- ID 一旦得到 Search-backed 证明，后续可以继续出现为多个严格空占位；每次出现都必须有独立的 `response.output_item.done`。
- “严格空”要求 visible summary/content 为空，且不存在 summary/raw lifecycle；允许有界 opaque `encrypted_content`，但它不成为可见 reasoning，也不会导致保存 raw 明文。
- `response.incomplete` 不能吞掉尚未 `output_item.done` 的复用段；所有复用段闭合后，后续 max-token 终态仍按既有契约完成。原项未闭合、首次复用前无完成 Search、跨类型、非空 summary/raw、未知 terminal 字段或 accessor-backed Search item/response container 字段继续失败关闭。
- 完成态 Web Search 只接受精确 `open_page` action 和有界的 `{ type: "open_page", url }`；streamed 与 final action 的 type/URL 必须一致。
- Provider 校验后立即丢弃 `open_page` URL，不打开、不预览、不下载、不 replay，也不把远端 Search 伪装成 Harness 本地工具调用。
- Search terminal item 与外层 response 字段先捕获 own-data 快照再分派、对账；自修改 accessor 不会被调用。ID 已 Search-backed 后的后续复用不再反复扫描先前 Search。

### 真实协议验证

在仓库所有者明确授权测试的已登录账号环境中，本版完成了两层脱敏复验；该测试授权与后续精确制品发布授权分别留证：

- 原始协议：Web/X 各 1 次请求、各 64 个事件，分别观察到对应 Search，终态均为 `completed`；
- 生产 adapter：direct Web/X 均以 `stop` 完成；
- Harness 形状：本地 `x_search` call/result 续跑三轮依次为 `tool-calls`、`tool-calls`、`stop`，前两轮各 1 次本地调用。连同 direct Web/X 共 5 次 Responses。该续跑没有在同一 wire request 中同时放入 Harness `x_search` function definition 与 xAI `{ type: "x_search" }` server descriptor；`1.0.1` 后续才隔离出这一 HTTP 400 冲突。

探针没有保存或输出搜索结果、URL、prompt、账号身份或凭据。它们证明本版协议方向能完成观察到的真实流程，但不替代 OAuth、完整桌面会话或 Windows 真机验收。

`1.0.0` is published. It repairs remaining `The Grok provider rejected an invalid or unsupported response` failures in real `grok-4.6` Web/X Search streams: after one completed Search, the upstream may emit multiple empty placeholder lifecycles for the same reasoning ID, and a completed Web Search may return an `open_page` action.

### Install

Current stable release:

```sh
dsh plugin --profile web add dsh-grok-provider@1.0.0
dsh web
```

### Fixes

- Before the first reasoning-ID reuse, the original lifecycle must close and one completed Web/X server Search must lie between the two items.
- Once Search-backed, that ID may continue through multiple strictly empty placeholders, each with its own `response.output_item.done`.
- "Strictly empty" means empty visible summary/content and no summary/raw lifecycle. A bounded opaque `encrypted_content` value is allowed, but is not visible reasoning and does not retain raw plaintext.
- `response.incomplete` cannot swallow a reused lifecycle that has not reached `output_item.done`; after every reused lifecycle closes, a later max-token terminal remains valid. Still-open, pre-Search, cross-type, non-empty summary/raw, unknown-terminal, and accessor-backed Search-item/response-container shapes continue to fail closed.
- A completed Web Search `open_page` action accepts only exact bounded `{ type: "open_page", url }`; streamed and final action type/URL must match.
- The Provider discards the validated URL and never visits, previews, downloads, or replays it, nor projects remote Search as a local Harness tool call.
- Search terminal items and outer response fields are captured as own-data snapshots before dispatch and reconciliation, so self-replacing accessors are never invoked. Later reuses of an already Search-backed ID do not rescan prior Search calls.

### Real protocol verification

With the repository owner's explicit permission to test in the already authenticated account environment, the release completed two-layer redacted verification. That test permission and the later exact-artifact publication authorization were recorded separately:

- Raw protocol: one 64-event response each for Web and X, with the requested Search kind observed and terminal `completed`;
- production adapter: direct Web and direct X both completed with `stop`;
- Harness-shaped flow: a local `x_search` call/result continuation ended `tool-calls`, `tool-calls`, then `stop`, with one local call in each of the first two turns. Together with direct Web/X, this made 5 Responses calls. The continuation did not place a Harness `x_search` function definition beside an xAI `{ type: "x_search" }` server descriptor in the same wire request; `1.0.1` later isolated that combination as an HTTP 400 conflict.

The probes did not retain or expose results, URLs, prompts, account identity, or credentials. They verify the observed protocol direction, not OAuth, a complete desktop session, or real-device Windows acceptance.
